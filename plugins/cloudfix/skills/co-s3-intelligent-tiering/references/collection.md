# Collection: S3 configuration and CloudWatch metrics

Read this in stage 2 of `SKILL.md`, in every pricing mode. It gives the exact reads, request shapes, paging, error handling and metric reduction. Save every request, page, response or error and timestamp in the evidence folder.

Use the regional S3 and CloudWatch endpoints. Record request shapes and collect every page. Supplied evidence uses the same shapes and fixed observation clock.

For user-selected buckets or inventory discovery, report the actual inventory coverage. This replaces CUR discovery; account scope, historical tags and unknown tenant threshold/settings are not proven by `ListBuckets`. A completed paginated inventory with no candidates is a successful empty result. A missing/denied inventory is not empty. No candidates skips billing queries.

1. `ListBuckets({BucketRegion: region})` through all `ContinuationToken` pages. The endpoint region must match `BucketRegion`. Keep buckets with a non-nullish `Name`, and map by `Name` (last duplicate wins). Missing `Buckets` is normalized by the source to `[]`; an absent response is never a successful empty list.
2. For each selected resource ID, `GetBucketTagging({Bucket: resourceId})`. Source catches every tagging error and continues without tags; preserve the error and mark tagging unchecked. A live `dont_fix_it` tag is not an extra native validator; CUR discovery handles its historical counterpart. Surface such user constraints separately before any proposal.
3. Only for selected buckets present in the regional listing, `GetBucketLifecycleConfiguration({Bucket})`. Keep rules with a non-nullish `Status`; preserve rejected malformed entries as input-quality evidence. `NoSuchLifecycleConfiguration` means successful absence. `NoSuchBucket`, or an `AccessDenied` whose message contains `resource-based policy`, marks that bucket unreadable with `"<name>: <message>"`. Other failures propagate as batch/read failures; never represent them as no rules.
4. `ListBucketIntelligentTieringConfigurations({Bucket})` for the same existing buckets, using `ContinuationToken` while `IsTruncated` and `NextContinuationToken` indicate another page. Keep configurations with non-nullish `Id`, `Status`, `Tierings`; preserve all raw entries. Native `Code=NoSuchConfiguration` or `Code/name=NoSuchBucket` is treated as no configuration (including deletion after listing). A `Code` or `name` containing `AccessDenied` records the error code/name and emits an unchecked warning later. Other errors propagate. Missing response/page is not no configuration.
5. Collect the following S3 CloudWatch daily metrics. Native setup starts listing, tagging and the three metric groups together; lifecycle waits for the listing, then IT configuration is read after those groups complete. Evaluation starts after collection. A guided run may issue lifecycle and IT configuration reads as soon as the listing exists, and in Cost Explorer `billing` the billed-size series below is a fourth group; the order of these read-only calls changes no value. A local harness may perform the same read-only operations sequentially if needed, recording timestamps; it must not claim an atomic snapshot.

Each `GetMetricData` query has a unique valid ID and this shape:

```json
{"Id":"bucket_0_metric_0","MetricStat":{"Metric":{"Namespace":"AWS/S3","MetricName":"<metric>","Dimensions":[{"Name":"BucketName","Value":"<bucket>"},{"Name":"StorageType","Value":"<type>"}]},"Stat":"Average","Period":86400}}
```

No `Unit`, `ReturnData` or `ScanBy` is set by the native caller. Set request `StartTime=UTC midnight(asOf)−lookbackDays*86400 seconds`, `EndTime=asOf`; retain the generated ID→bucket/series mapping. Split at AWS's 500-query limit and follow every `NextToken`. Preserve page order.

| Group | Lookback | Metric / StorageType | Reduction |
| --- | --- | --- | --- |
| Object count | 90 days | `NumberOfObjects` / `AllStorageTypes` | Pair timestamps with values (missing paired value becomes 0), sort ascending, take last value; absent series data leaves latest count undefined. |
| Tier sizes | 3 days | `BucketSizeBytes` / storage types below | First value in response order for each type; missing/non-finite first value becomes 0. Sum types per tier, divide by `1024^3`, then `Number.parseFloat(sum.toFixed(2))`. |
| Archived objects | 3 days | `BucketSizeBytes` / `GlacierObjectOverhead`, `DeepArchiveObjectOverhead` | Sum each series' first value (same zero handling), divide by `32*1024`, then `Math.round`. |

Tier mapping is exact: `standardGb=StandardStorage`; `standardIaGb=StandardIAStorage`; `onezoneIaGb=OneZoneIAStorage`; `intelligentTieringGb` sums `IntelligentTieringFAStorage`, `IntelligentTieringIAStorage`, `IntelligentTieringAIAStorage`, `IntelligentTieringAAStorage`, `IntelligentTieringDAAStorage`; `glacierIrGb=GlacierInstantRetrievalStorage`; `glacierGb=GlacierStorage`; `deepArchiveGb=DeepArchiveStorage`. This is 11 tier-size queries, two overhead queries and one object-count query per bucket.

**Billed-size series, Cost Explorer `billing` only.** Add two queries per bucket with the same shape: `BucketSizeBytes` for `StandardStorage` and for `StandardIAStorage`. Unlike the three metric groups above, set `StartTime=UTC midnight(asOf)−8 days` and `EndTime=UTC midnight(asOf)−1 day` (exclusive). This seven-day window matches the daily CUR rows selected by `references/billing-cur.md`, including its one-day reporting lag. For `asOf=2026-11-19T12:00:00Z`, the window is `[2026-11-11T00:00:00Z, 2026-11-18T00:00:00Z)`. Keep every datapoint. Average only datapoints with `StartTime <= timestamp < EndTime`; preserve any datapoint outside that window in the evidence, unaveraged. A null, non-finite or negative value, or a timestamp repeated across pages, is a fault of that bucket, never 0 and never counted twice. The reduction is the mean of the daily values the series returned, divided by `1024^3`, then `Number.parseFloat(mean.toFixed(2))`; a day the series did not return is not filled in, and the count of returned days is recorded as `sizeDays`, per class: `{"standard": n, "standardIa": m}`. A series that returned no day gives 0 for its class only when that class's first-value size above is also 0. If the class holds bytes today but its series returned no day, or its mean is 0, the bucket has no billed size and no economic row: it is `needs_evidence`, with one `missing_evidence` issue at stage `collection` that names the bucket and the series, and `request: {"kind": "aws_read", "name": "GetMetricData", "service": "cloudwatch", "region": "<bucket region>"}`. A bucket that a completed check rejected stays `not_recommended`. A class with fewer than 7 returned days is priced on the days returned, and the top-level `qualifications` name each such bucket with its count. The results are `standardGbBilled` and `standardIaGbBilled`. They price the economic row in `references/billing-cost-explorer.md` and nothing else: the checks keep the first-value `standardGb` and `standardIaGb` above. The native finder prices a seven-day CUR window, which is the average size over that week, and measures object fees on today's bytes; a bucket that grows or shrinks by a few percent a day therefore prices differently today than over the week, and the week is what CloudFix reports.

Merge paginated metric results by ID and the first returned label: concatenate timestamp/value arrays for that label and retain the last page's status. An `InternalError` or `Forbidden` on any page faults its owning bucket; a fault whose ID cannot be attributed faults the whole request pack. A missing expected result ID or a final `PartialData` is a fault, distinct from an explicit result with empty arrays. For these native S3 queries, absent final status and informational messages are not independently rejected; preserve them and their uncertainty. Per-bucket metric faults produce an `Exception` at the object-metrics stage, with the original error and resource; an IAM/request failure propagates at collection. Do not fabricate zero metrics from either.

The native choice of the latest available count within 90 days and first returned tier-size values does not require common timestamps, measure freshness skew, or check proportional disagreement with CUR. Preserve all timestamps and flag that limit; do not claim the count, storage and CUR describe one instant.
