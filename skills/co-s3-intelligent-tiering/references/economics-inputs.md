# Economic inputs

Read this in stage 1 of `SKILL.md` once the pricing mode is known, for `supplied`, `billing` and `public_prices`. It defines the economic row that the savings checks and the fee function consume, and what must never stand in for it. The Cost Explorer effective-rate method is in `references/billing-cost-explorer.md`; the CUR query, for a customer-supplied export, is in `references/billing-cur.md`; the public-price model is in `references/public-price-model.md`. A `technical_only` run has no economic row.

**Which source supplies billed cost.** A customer cannot be assumed to have a CUR, so a billed-cost request (`billing`) uses Cost Explorer by default: `references/billing-cost-explorer.md` derives an account-and-region effective rate for Standard and for Standard-IA storage and applies it to each bucket's 7-day mean size. That is an account rate applied to a measured size, labelled `account_effective_rate`. It is not that bucket's bill, and is never presented as one or as CUR-equivalent. The CUR query is used only when the customer supplies a resource-level CUR export, and its rows stay `resource_billed`. Never mix the two in one assessment.

**No silent substitution.** A billed-cost request is never answered with public prices. When Cost Explorer is denied or returns no usable usage, the affected rows are an error or missing evidence, as `references/billing-cost-explorer.md` states. Public prices may follow only a conditional request in the customer's own words, such as "use billed costs if possible, otherwise public prices": try Cost Explorer first; if it lacks any rate the run needs, say exactly which and why, then run the public-price model for the whole run, saved and labelled as `public_prices`.

The public-price model is an explicit harness extension; native supplied/CUR calculations remain unchanged. The Cost Explorer effective-rate model is a second explicit extension: it feeds the same storage model, checks and fee function, with billed rates in place of catalog rates. Do not invent a discount or infer object access from object counts. CE can expose opt-in daily S3 resource data, but accept it only when actual records prove bucket identity, account/region, period, usage classes and coverage; this skill does not enable billing settings or invent an undocumented query. A public rate supplies storage pricing, not a measured future tier mix. An effective rate supplies billed storage pricing, and no tier mix either. Supplied exact fields remain valid offline with their provenance.

**Native economic row.** Each native quantitative resource contains `resourceId` (bucket name), `awsAccount`, `awsRegion`, `resourceName`, `publicAnnualCost`, `annualCost`, `totalSavings`, `extraSavings`, `dataSavings`, `totalSavingsPercentage`, `dataSavingsPercentage`, `girGbMonths`, `iaGbMonths`, `stdGbMonths`, `gbMonths`, `dataCosts`, `intMonitoringCosts`; retain any supplied `warning` and additional metadata. The `*GbMonths` fields are **average GB sizes over the CUR window's storage days**, despite their names. `intMonitoringCosts` is the annual list-price monitoring charge from the smallest billed day. Economic inputs must have an explicit common currency; the source's fixed fees are USD, so another currency cannot be compared without separately authorized, evidenced conversion. Never overwrite supplied facts to make a result pass.

The native parser uses `Number.parseFloat` and converts NaN to `0` for every numeric field; it does not validate missing billing facts. Preserve this normalization when reproducing a raw native query row, alongside the original values and missing-field flags. A normalized zero from missing/malformed input is not evidence of zero charges and does not justify a complete skill assessment. A supplied camel-case numeric resource is already parsed: do not reparse it or round it anew. In replay, keep missing `intMonitoringCosts` distinct even though the validator's formula uses zero credit for a non-finite/missing value.
